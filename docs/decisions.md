# Decisions

Why things are the way they are. Newest at the bottom; a decision that gets replaced stays here, marked as such.

| # | Decision | Why | Alternatives considered |
| --- | --- | --- | --- |
| 1 | **Self-hosted LiveKit** for video | An SFU uploads each screen once and fans it out; open source, Docker image, good browser SDK | Peer-to-peer mesh (every viewer costs the sharer upload bandwidth), hosted services (cost, data leaves our server) |
| 2 | **One room, one screen slot** in version 1 (screens replaced by decision 32) | The product is "watch my screen with friends"; the limit is kept as a limit so more screens can come later | Rooms, multiple screens from day one |
| 3 | **No camera, no microphone** (cameras allowed by decision 32; still no microphone) | Scope: voice already happens elsewhere; fewer permissions to ask for | — |
| 4 | **Monorepo** (`api/`, `web/`, compose, docs) with a separate private repo for the shared proxy | The app repo knows how to run the app; the infra repo knows how to reach it | One repo per service |
| 5 | **Java 21 + Spring Boot** for the API | Mature security and data libraries; the backend stack most job postings ask for | Node/TypeScript end to end |
| 6 | **Google sign-in + request access + admin approval** | Real identities without passwords; approving people in the app instead of editing a list | Fixed allowlist in configuration |
| 7 | **Server-side sessions** in PostgreSQL (Spring Session JDBC) | Removing a member can end their sessions immediately | Stateless JWT sessions |
| 8 | **Screen slot in API memory**, polled every 2 s (now the seats and streams, decision 32) | One instance and a few people: simple and enough | Database table, LiveKit room metadata, WebSockets |
| 9 | **LiveKit tokens signed with Nimbus JOSE** | Already on the classpath through Spring Security; one small class | LiveKit's server SDK |
| 10 | **Take over = steal, after a confirmation** (replaced by decision 32: nobody is pushed out) | Friends, not strangers: whoever wants the screen gets it | Refuse while busy; ask the sharer |
| 11 | **Screen audio allowed, never a microphone** | Watching a game or a video needs its sound | Screen only |
| 12 | **LiveKit media on one UDP port** (plus a TCP fallback) | One firewall rule instead of a 10,000-port range; fine for a small group | Port range |
| 13 | **Caddy** as the shared reverse proxy | Automatic HTTPS, short config | nginx + certbot, Traefik |
| 14 | **Caddy everywhere**: the web image serves the build with Caddy built from source on the latest Go (same recipe as the proxy, decision 21), running as a non-root user | One web server to know instead of two, with a short config; building from source keeps it free of HIGH/CRITICAL findings | nginx inside the web image (a second server and config style to maintain); the official Caddy image (lags behind Go's security releases) |
| 15 | **Trunk-based: `main` + release tags** (replaced `develop` → staging, `main` → production) | One long-lived branch; production gets the exact image staging tested | Git flow with `develop` and `main` |
| 16 | **Build once, promote**: images built in CI, servers only pull | What's tested is what runs; fast deploys; rollback = previous image | Building on the server |
| 17 | **Pipeline stages: build → validate → tests + vulnerability scan + SAST → publish → deploy with rollback** | Catch problems in the cheapest place; nothing unscanned is published | Tests only |
| 18 | **Trivy and Semgrep** for scanning | Free, run anywhere (no paid code scanning needed for a private repository) | CodeQL (free only for public repositories), Snyk |
| 19 | **Deploy over SSH with a forced-command key** | The key can only run the deploy script | Self-hosted runner on the server, webhook-triggered deploys |
| 20 | **Checks on every commit**, one reusable workflow shared with the stage release | Problems show up on the commit that caused them, before a pull request; one definition of "passes" | Checks only on pull requests |
| 21 | **The proxy runs Caddy rebuilt from source** on the latest Go with updated libraries, rebuilt weekly by CI | The official Caddy image lagged behind Go's security releases (17 HIGH findings, mostly denial of service); rebuilding fixed all of them and keeps automatic HTTPS | Migrating the proxy to nginx + certbot (more moving parts, risky switch, same result). The web image uses the same recipe (decision 14) |
| 22 | **Spec-driven development on GitHub Issues**: issue → approved spec → approved plan → tasks → PR proving every acceptance criterion; Claude Code commands for each stage | The trail from need to deployed code is visible in one place, next to the code; mirrors a Jira workflow without a second tool | Jira, Slack for backlog, GitHub's Spec Kit (heavier) |
| 23 | **Pipeline results go to Discord** through a channel webhook, for every stage release (success and failure) | Already where Henrique looks; one secret, nothing to host; success messages confirm what's live | Email over SMTP (needs a mailbox and three secrets), a Discord bot (hosting and a token for the same result) |
| 24 | **LiveKit webhooks free the screen slot** when the sharing connection leaves or its screen track stops ([spec 0038](../specs/0038-stale-slot/spec.md)); one connection per person | LiveKit already knows at once; signed events, nothing to poll | The API polling LiveKit's participant list; heartbeats from the sharer's browser; one identity per connection (several devices at once) |
| 25 | **Platform split**: `xove` holds only the app (code, Flyway migrations, Dockerfiles, a compose file for local dev and CI); `infra` holds everything that runs on the VPS (proxy, shared LiveKit, each environment's compose and Postgres, deploy, backups); a `pipelines` repo holds the CI/CD templates that repos reference by version. Public settings per environment live in `infra/config/<env>.yaml` (in git); secrets only in 1Password; one `.env` per environment is generated from both (#43) | The app stays self-contained and portable; the server never has the app's source; one place for pipeline logic. Milestone "Platform split" (#43 vault first, then #44, #67, #68, #69: infra released like the app, staging on merge and production on tag), before backups | Keeping `ops/` and the server compose in the app repo (simpler, but mixes the app with how it runs); one repo for everything |
| 26 | **The app owns its shape; `infra` owns values and the deploy** (refines #25): `xove`'s `compose.yaml` is the single definition of its services (images, ports, networks, the names of the variables it needs, with `${VAR:?}` for required ones), used by local dev, CI and the servers. `infra` holds the per-environment values (`config/<env>.yaml` plus the vault), the shared services (proxy, LiveKit) and the deploy tool, which runs the app's compose file at the deployed commit with that environment's generated `.env`. What runs in production is recorded in git (release tags) | No drift between two Compose files; the same split as app-owned manifests plus environment config in larger setups (Helm charts plus GitOps values); the deploy script never comes from the public app repo | A second Compose file for the app in `infra` (drift); the app repo deploying itself (the public repo would control a script with server access) |
| 27 | **Secrets in two 1Password vaults, read at run time** ([spec 0043](../specs/0043-secrets-vault/spec.md)): `Xove App` for running services (read by the server's service account) and `Xove CI` for the pipeline (read by its own service account, the only GitHub secret); each environment's `.env` is generated by `infra/ops/build-env` from `infra/config` and the vault; the pipeline no longer checks staging from outside | One source for every secret; a leaked CI token can't read the database password; rotation is "change in 1Password, rebuild, restart"; the stage cookie never leaves the runtime vault | One vault (the CI token could read every secret); secrets copied into GitHub Actions (two sources of truth); 1Password Environments (secrets and public settings mixed outside git) |
| 28 | **One LiveKit server per environment**, both run from `infra` ([spec 0044](../specs/0044-livekit-in-infra/spec.md)): own key pair, address (`rtc-stage.xove.app`, `rtc.xove.app`), media ports (7881/7882, 7883/7884) and room | LiveKit keys aren't tied to rooms, so one shared server would let a leaked staging secret reach production; full separation costs only two more media ports | One shared LiveKit with a room per environment (isolation by tokens only); one Docker network per environment (too much setup for one VPS) |
| 29 | **The server deploys from `infra` with the app's own `compose.yaml`** ([spec 0067](../specs/0067-deploy-from-infra/spec.md)): no checkout of `xove` on the server; `infra/ops/deploy.sh <app> <env>` downloads the compose file of the deployed commit from GitHub; "healthy" is defined by `healthcheck:` entries in the app's compose file. Only commits on `main` deploy, and the compose file is checked as untrusted (only the app's own images, volumes and networks; nothing that reaches the host) | The deploy script can't be changed from the public repo; the server holds no source; one tool for every app and environment; CI and the server share one definition of healthy; a branch, a fork or a bad compose change can't run arbitrary containers with the server's settings | Keeping `ops/` in the app (the public repo controls a script with server access); publishing the compose file with the images (more to build now); a health script per app in `infra` |
| 30 | **Production is released only from a version tag, by its own pipeline** ([spec 0046](../specs/0046-production-environment/spec.md)): `release.yml` checks the commit's stage release was green, adds the version tag to the same images, deploys with a key that can only deploy production, checks `xove.app` from the internet, and rolls back by itself if that check fails; its "Run workflow" button runs only the rollback. Production has its own database, Google OAuth client, LiveKit server and room | The tag is the approval, and what runs in production is recorded in git; production runs exactly what staging tested; no manual deploys means nothing on the server drifts from git | Deploying production by hand with the deploy tool; one pipeline for both environments; rebuilding images for production; one deploy key for both environments |
| 31 | **Screens are sent for motion and sound, within a budget** ([spec 0086](../specs/0086-stream-quality/spec.md)): presets 1080p, 720p and 480p at 30 fps; VP9 with one layer per quality (VP8 where the browser can't); Smooth (frame rate first) or Sharp (detail first); screen sound without microphone filters, stereo, 128 kbit/s, no silence skipping; viewers pick Auto or a fixed quality and their own volume; a setup window after the picker; the sharer's quality is a cap they change live, shared through the API so viewers follow it and LiveKit stops sending the layers above it | LiveKit's defaults (15 fps, sharpness first, voice filters) made shared games look like slides and music sound bad; per-quality layers give viewers exactly 1080p, 720p or 480p and keep a full room within the VPS's traffic; ceilings of 8, 4 and 2 Mbit/s per layer, high on purpose, so only each person's computer and connection limit the picture (the VPS's traffic is watched in Hostinger's panel instead); Firefox and Safari sharers send a single layer | republishing the stream on every change (a reload for viewers, and the API had to follow a new track); VP8 (lighter on the sharer's CPU, more bandwidth; the fallback if VP9 drops frames); VP9 as one stream with layers inside (halves the size at each step: 1080p, 540p, 270p); LiveKit's 5 Mbit/s 1080p preset; tight per-quality budgets (2.5, 1.2, 0.6 Mbit/s) to protect the VPS's traffic |
| 32 | **Several streams and a room with seats** ([spec 0060](../specs/0060-several-streams/spec.md)): up to 6 live streams (a screen or a camera each; never a microphone), nobody pushed out; 20 seats (`XOVE_ROOM_SEATS`), a LiveKit token only with a seat, then a queue where a free seat is offered for 60 seconds; a seat or place kept 30 s after a closed tab, 60 s after a drop (LiveKit's `disconnectReason`); each viewer picks who is big, the others are thumbnails, and screen with camera shows a facecam; everything in API memory, registered again by the browsers after a restart | Friends showing each other things at once; the SFU keeps each viewer's download to what they watch big; the VPS has the bandwidth (8 TB a month, watched in Hostinger's panel) | Peer-to-peer mesh (each sharer's upload grows with every viewer); a fixed bandwidth budget; LiveKit's `max_participants` alone (can't queue or keep a place); the database for seats and streams; timers instead of tidying on each request |
| 33 | **A shared window sends only its app's sound** ([spec 0095](../specs/0095-app-sound/spec.md)): the picker asks for `windowAudio: "window"`, and the whole screen leaves out Xovê's own sound (`restrictOwnAudio`); Xovê calls `getDisplayMedia` itself and wraps the tracks in LiveKit's types | Sharing a game's window sent the whole system sound, Discord included, so friends heard themselves; livekit-client (2.22.3) drops `windowAudio`; a browser can't leave one app out of a full-screen share | patching livekit-client (lost on every upgrade); waiting for LiveKit to support the option; only `restrictOwnAudio` (fixes Xovê's own echo, not Discord's); a native helper app recording per app (an install for every sharer) |
| 34 | **My screen and camera are round buttons on the player** ([spec 0098](../specs/0098-player-buttons/spec.md)): no bar under the player; while live, an arrow opens each stream's menu (quality, mode, change window or camera list, stop); "Change window" and a new camera swap the same LiveKit track instead of stopping; the sharer's own player has no settings | Like Discord: the controls sit where people look, fade with the player and work in fullscreen; one place for a stream's settings; swapping keeps viewers watching without a break and the API sees the same stream | keeping the bar, restyled (doesn't fade or follow fullscreen); one gear menu for both streams; stopping and starting again to change window or camera; a menu library |
| 35 | **One row of round controls on the player** ([spec 0101](../specs/0101-player-polish/spec.md)): volume, screen, camera, settings, centred; a vertical volume slider on hover or focus, none while muted or without sound; the viewer's quality in a gear menu; shared pill and menu pieces; Chrome asked to stay on Xovê after the pick; the setup window drawn inside fullscreen | The viewer's old bar didn't match the round buttons and always showed its slider; Chrome jumped to the picked window, hiding the setup window; in fullscreen the setup window opened behind the player | a separate viewer bar on the left; a pure CSS hover slider (fades under the pointer, untestable); `writing-mode` for the vertical slider (needs Chrome 124); leaving fullscreen before the picker |
